# 프로젝트 목표와 사용자 요구

사용자의 목표는 카카오톡 업무를 프로그램에 맡기는 것이다. 대화를 읽는 일, 명단을 맞추는 일, 파일을 보내는 일, 지정 시각에 예약하는 일을 줄이려 했다. 대상과 내용이 틀리거나 성공 표시가 실제 결과와 다르면 자동화의 의미가 없었다.

특히 예약에서 원한 결과는 명확했다. **CSV의 모든 메시지를 각 대상과 시각에 맞춰 자동 등록하는 것**이다. 기능을 만들 수 있다는 설명보다, 실제 작업이 끝나고 다음 파일에도 재사용되는 결과가 필요했다.

## Spoiler에서 원한 경험

사용자는 PC 카카오톡의 대화창을 열지 않고 내용을 보고 싶었다. 핵심 표현은 **‘1을 없애지 않고 읽기’**였다. 알림에 우연히 나타난 글만 모으는 기능으로는 이 목적을 충족하지 못했다.

이후 요구는 카카오톡과 비슷한 대화 화면으로 구체화됐다. 사람별 발언 목록보다 실제 대화방의 흐름이 중요했다. 단톡방에서도 내 메시지와 여러 상대의 메시지가 시간순으로 이어져야 했다. 방 이름, 검색, 시각 찾기, 방별 초안과 직접 답장도 필요했다.

| 사용자 요구 | 현재 구현 | 해석 범위 |
|---|---|---|
| 읽음 표시를 보내지 않고 원문 열람 | 태블릿 세션 수신과 읽기 전용 내역 조회. 열람 경로에 읽음·입장 명령을 연결하지 않음 | 다른 카카오톡 기기에서 읽는 동작은 제어하지 않음 |
| 실제 대화방 단위 표시 | 방 ID로 묶고 내·상대 메시지를 시간순 표시. 단톡방 포함 | 방을 확인할 수 없는 옛 기록은 별도 읽기 전용 영역에 보존 |
| 익숙한 방 이름 | 사용자 지정 제목, 동기화된 친구 이름, 참가자 정보를 보완하고 늦은 결과도 반영 | PC에만 있고 서버에 동기화되지 않은 이름까지 같다고 보장하지 않음 |
| 꺼져 있던 동안의 메시지 보완 | 저장된 복구 지점과 발견한 방을 기준으로 내역을 순차 조회 | 서버 제공 범위와 처리 한도가 있음. 모든 과거 대화의 완전 복구는 아님 |
| 메시지 수가 늘어도 다른 방 유지 | 전체 최신 1,000개·최대 7일 보관 | 7일간의 모든 메시지를 저장하는 기준은 아님 |
| 필요할 때만 창을 열기 | 트레이 수신, 창 복원, Windows 로그인 시 자동 실행 설치 도구 | 창의 X는 숨김. 완전 종료는 트레이 메뉴에서 수행 |
| 사용자가 직접 답장 | 선택한 방에 텍스트 직접 전송. 방별 초안, 중복 클릭 차단 | AI 답장은 없음. 답장 후 상대방의 ‘1’ 유지까지 일반적으로 실측한 것은 아님 |

현재 동작은 [Spoiler 안내](../../spoiler/README.md), [대화방 UI 기록](../SPOILER_ROOM_UI_2026-09-30.md), [대화 통합 기록](../SPOILER_CONVERSATIONS_2026-09-30.md)에서 확인할 수 있다. 초기 문서의 80개 보관 수는 이후 1,000개로 바뀐 과거 값이다.

## KakaoSender에서 원한 경험

사용자는 CSV를 넣은 뒤 대상과 내용을 확인하고 한 번에 처리하려 했다. 대화명과 방 ID의 매칭을 매번 다시 만들거나, 파일을 준비하는 순간 마우스가 움직이는 동작을 원하지 않았다. 직접 전송은 화면 조작 없이 서버에 보내는 기능으로 이해했다.

| 사용자 요구 | 현재 구현 | 해석 범위 |
|---|---|---|
| CSV·XLSX 명단으로 일괄 처리 | 미리보기, 편집, 공통 첨부, 행별 예약, 발송 방식 표시 | 파일을 읽거나 미리보기를 바꾸는 것만으로 발송하지 않음 |
| 매칭 결과를 저장하고 재사용 | 확인한 대화명과 방 ID를 저장. 필요한 ID만 조회하고 발송 전 검증 | 동명이인·충돌·불완전한 근거는 임의로 맞추지 않음 |
| 화면 없는 텍스트·파일 발송 | 직접 전송 ON에서 본문과 이미지·PDF 등 첨부를 서버로 전송 | 비공식 SDK·프로토콜 경로다. 카카오 공식 제3자 메시지 API라는 뜻은 아님 |
| 파일을 쉽게 지정 | 파일 선택, 경로 입력, 첨부 패널 드래그앤드롭 | 지정은 준비 단계다. 공통 첨부는 모든 대상 행에 적용 |
| 모든 대상이 같은 파일 받기 | 실행 시작 때 원본을 복사하고 그 내용을 재사용 | 원본을 수정·삭제해도 현재 실행은 복사본을 사용. 새 실행은 다시 준비 |
| 대량 발송에서 불필요한 대기 줄이기 | 기본 30대상 행 처리 후 2초 대기, 다음 묶음 진행 | 건별 2초 강제 대기가 아님. 카카오의 보장된 허용 한도를 뜻하지 않음 |
| CSV 대상·시각대로 예약 등록 | GUI와 CLI가 같은 Windows 예약 자동화와 기록 사용. LLM 없이 실행 | 현재는 텍스트 예약. 예약창·OCR을 사용하므로 화면 사용이 필요 |
| 중단 후 남은 행 이어서 처리 | 시도와 결과를 저장하고 미시도·발송 전 중단 행을 복원 | 접수 완료와 결과 불명 행은 자동 재전송하지 않음 |
| 예약 100개 한도 초과 예방 | 등록 기록과 PC 시각으로 슬롯 추정. 묶음 시작과 행별 확보에서 검사 | 다른 기기의 수동 등록·취소와 서버 지연은 자동 반영하지 않음 |

동작 기준은 [루트 사용 안내](../../README.md)와 [CSV 예약 안내](../NATIVE_RESERVATIONS.md)에 있다.

## ‘직접 전송’과 ‘예약’의 구분

| 작업 | 실행 경로 | 등록·전송 중 화면 사용 | 현재 구현 여부 |
|---|---|---|---|
| 직접 전송 ON의 즉시 텍스트·파일 | Node 브리지에서 서버 전송 | 없음 | 구현 |
| Spoiler의 직접 답장 | 태블릿 세션에서 서버 전송 | 없음 | 구현 |
| 카카오톡 네이티브 예약 등록 | Windows 카카오톡 예약창 조작 | 있음 | 구현 |
| 서버 API로 네이티브 예약 직접 등록 | 예약용 요청 계약 필요 | 없음을 목표로 함 | 미구현 |
| Hub가 시각까지 기다렸다가 직접 발송 | 로컬 타이머와 작업 큐 필요 | 직접 전송 자체에는 없음 | 현재 제품에 구현하지 않음 |

사용자는 노트북을 켜둘 수 없는 경우에도 예약을 쓰고 싶었다. 그래서 카카오톡에 미리 예약을 저장하는 방식을 선택했다. 로컬 타이머로 대체하는 제안은 이번 요구의 채택된 구현이 아니다.

예약 등록에 AI가 필요하지 않은 것과, 화면이 필요하지 않은 것은 서로 다른 조건이다. 현재 코드는 AI 없이 동작하지만 Windows 화면을 사용한다. 직접 예약 프로토콜 조사는 구현 성공으로 이어지지 않았다.

## 사용자와 함께 정한 제품 기준

1. 결과 불명을 성공이나 미발송으로 단정하지 않는다. 확인 전에는 다시 보내지 않는다.
2. 불완전한 목록에서 빠졌다는 이유만으로 확인한 매칭을 지우지 않는다. 실제 충돌은 별도로 막는다.
3. 파일 등록·검색·열람·초안 입력은 외부 발송 동작과 분리한다.
4. 실행 중 원본 첨부가 바뀌어도 실행 시작 때의 내용을 유지한다.
5. 예약 슬롯이 부족하면 전체 파일을 무리하게 등록하지 않는다. 실제 160건 작업은 54건을 먼저 처리하고 남은 106건을 주간 파일로 나눴다.
6. 버튼 상태, 결과 수, 처리 중 표시가 실제 실행 상태와 같아야 한다.
7. 한국어 원문, 공백, 입력한 줄바꿈과 복사 내용을 보존한다.
8. 이미 쓰는 Tkinter와 WPF를 유지한다. 디자인 때문에 프레임워크나 여러 UI 라이브러리를 추가하지 않는다.

## 남은 염원

서버 직접 예약 등록은 여전히 남은 목표다. 기간별 메시지 전체 수집과 CSV 내보내기, 결석·보강 내용 분류, AI 답장도 현재 제품의 완료 기능이 아니다. 내역 조회와 별도 AI 정리를 연결할 수 있다는 가능성을 제품 구현 완료로 표시하지 않는다.

새 기능의 완료 기준은 사용자가 다시 같은 절차를 따라도 맞는 결과를 얻는 것이다. 확인하지 못하는 상황에서는 근거를 남기고 멈춰야 한다. [주요 오류 기록](INCIDENTS_AND_FIXES.md)은 이 기준을 정하게 된 이유를 설명한다.
