# Spoiler 대화방 UI와 직접 답장

2026-09-30 요청: 제공된 카카오톡 형태의 참고 화면을 바탕으로, 대화방별 원문을 읽음 처리 없이 읽고 사용자가 작성한 답장을 직접 전송한다. AI 답장은 포함하지 않는다.

## 구현

- 기존 WPF 앱을 유지하면서 방 목록과 대화 타임라인을 분리했다. 흰색 수신·노란색 발신 말풍선에 작성자, 날짜와 시각을 표시한다. 원문은 읽기 전용 텍스트 컨트롤로 선택·복사할 수 있다.
- 방 ID로 여러 작성자를 한 방에 묶고, 같은 제목의 서로 다른 방은 구분한다. 방 ID가 없는 기존 암호화 기록은 보존하면서 읽기 전용으로 표시한다.
- 검색·방 선택·시각 필터·내 메시지 숨김은 로컬 기록만 다룬다. 새 메시지가 와도 선택, 초안과 읽던 스크롤을 유지하며 맨 아래에서는 새 메시지를 따라간다.
- 전체 80개·최대 7일 보관 정책은 유지한다. 방의 숫자는 서버 안읽음 수가 아닌 로컬 보관 수다.
- 방별 초안과 명시적 전송 버튼, Ctrl+Enter 전송을 추가했다. Enter는 줄바꿈이다. 연결과 방 ID를 검증하고 송신 중 중복 클릭을 차단한다.
- 직접 답장은 SDK 세션의 단건 WRITE로 보내며 재접속 후 자동 재전송하지 않는다. 서버의 방·메시지 ID·시각과 암호화 저장 완료가 확인돼야 성공으로 처리한다. 실패·결과 불명 상태는 초안을 유지한다. 전송 도중 새로 쓴 초안이나 다른 방의 초안은 지우지 않는다.
- 계정·기기·연결 세대가 바뀐 답장 결과는 새 화면에 반영하지 않는다. 인증 파일 잠금 대기는 UI 및 수신 수명주기 잠금 밖에서 수행한다.
- 답장 접수 메시지는 복구 기준점을 앞당기지 않는다. 이름·방 제목 조회 중이던 이전 서버 메시지를 답장 ACK가 앞지르더라도 재접속 복구에서 빠뜨리지 않도록 했다.
- 실제 방 제목은 읽기 전용 조회로 보완한다. 작성자와 방 제목 조회를 합쳐 동시 4개로 제한하고, 방 제목은 최대 256개·60초 메모리 캐시로 재사용한다. 조회 실패·지연은 원문 수신을 막지 않는다.

## 검증 및 한계

격리된 가짜 서버·프로세스·WPF 앱으로 모델, 암호화 저장, 수신/재접속, 답장과 UI 계약을 검사했다. 860×800·760×560·1440×900 및 장문·빈 화면·전송 중·실패·결과 불명·기존 기록의 실제 WPF 렌더를 확인했다. 실사용 계정 로그인, 실제 메시지 발송과 데스크톱 제어는 수행하지 않았다.

수신 및 원문 열람 경로에는 markRead/NOTIREAD/CHATONROOM 호출을 추가하지 않았다. 직접 답장은 별도의 WRITE이며, 답장 송신 뒤에도 상대방의 ‘1’이 유지되는지 이번 작업에서 실측하지 않았다. 다른 카카오톡 기기에서 대화를 읽는 경우도 Spoiler가 제어하지 않는다.

증거와 이전 파일 백업: `exports/spoiler-room-ui-20260930/`. 최종 검사·적용 파일 해시는 해당 폴더의 `completion.json`, 소스 빌드 로그는 `stage-build.log`, 화면 검사는 `qa-report.json`과 `previews/`에 기록한다.

새 실행파일을 사용하려면 기존 트레이 메뉴에서 **완전히 종료**한 뒤 다시 실행한다. X 버튼은 기존과 동일하게 창만 숨긴다.
